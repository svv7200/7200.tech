# Метод построения корпоративного VPN

Практическая схема для компании с несколькими площадками, удалёнными сотрудниками и централизованным сопровождением. Основная задача — сохранить доступ к рабочим ресурсам и оборудованию, когда один из каналов перестаёт работать.

Это методика проектирования и эксплуатации. Она не является готовым установщиком или описанием конкретной действующей сети. Адресный план, ключи, учётные записи и параметры провайдеров определяются для каждого внедрения отдельно.

## Архитектура

Сеть разделяется на два контура: передача пользовательского трафика и управление оборудованием. Их отказ не должен происходить по одной и той же причине.

```text
Рабочие устройства
        |
Шлюз филиала ---- локальные сервисы и прямой выход
        |
        +---- основной узел передачи трафика
        |
        +---- резервный узел передачи трафика

Администратор ---- защищённый контур управления ---- шлюз филиала
                                                   |
                                      резервный канал управления
```

Резервный сервер у того же провайдера, за тем же внешним шлюзом и с общей системой DNS остаётся зависимым от этих компонентов. Действительная независимость определяется путём соединения, а не количеством профилей в приложении.

| Компонент | Назначение | Что проверять |
|---|---|---|
| Шлюз филиала | Маршрутизация, локальный DNS, подключение к узлам | Запуск после сбоя питания, сохранность настроек и списков |
| Основной узел | Передача выбранного трафика | Доступность приложений через него, а не только ответ сервера |
| Резервный узел | Работа при отказе основного | Отдельный провайдер или площадка, независимый маршрут |
| Контур управления | Доступ администратора к оборудованию | Вход при остановленном сервисе пользовательского трафика |
| Мониторинг | Обнаружение и локализация отказов | Состояние каналов и прикладные проверки с каждой площадки |

## Использованные инструменты

В практической реализации использовался следующий набор. Инструменты разделены по задачам: выдача профилей, передача трафика, управление шлюзами и сопровождение.

### Центральные узлы

| Инструмент | Роль в системе |
|---|---|
| Linux и systemd | Серверная среда, запуск служб, восстановление процессов и системный журнал |
| 3x-ui, семейство x-ui | Управление подключениями и клиентскими профилями, подписки, учёт трафика и автоматизация через API |
| Xray-core | Серверная обработка подключений, в частности VLESS с TLS или REALITY, и правила передачи трафика |
| Nginx | Веб-сервисы и публикация файлов правил маршрутизации |
| SQLite | Хранение данных панели и создание резервных копий; рабочие изменения клиентов выполняются через панель или API |
| Fail2ban | Ограничение повторных неудачных попыток входа на сервер |

Поддержка конкретного транспорта зависит от сборки панели и используемого ядра. Наличие Hysteria2 в одном развёртывании не означает, что любая версия x-ui или Xray поддерживает ту же конфигурацию. Панель управляет профилями подключений, но не заменяет корпоративную систему учётных записей и многофакторную аутентификацию.

### Шлюзы и маршрутизация

| Инструмент | Роль в системе |
|---|---|
| OpenWrt и LuCI | Настройка шлюзов филиалов, интерфейсов, локальных сетей и служб |
| podkop | Формирование правил выборочной маршрутизации и конфигурации sing-box на шлюзе |
| sing-box | Обработка выбранного трафика, DNS и подключений к основному и резервному узлам |
| WireGuard | Отдельный сетевой контур управления и доступ администратора к шлюзам |
| MikroTik RouterOS | Служебный WireGuard-хаб, маршруты и ограничения административного доступа |
| dnsmasq | Локальный DNS и DHCP; прямое разрешение служебных доменов независимо от пользовательского туннеля |
| firewall4 и nftables | Межсетевые правила, NAT и согласованный перехват DNS для устройств за шлюзом |
| procd и аппаратный watchdog | Запуск и перезапуск служб OpenWrt, восстановление при зависании устройства |

VLESS и Hysteria2 используются как транспорты передачи выбранного трафика. WireGuard отвечает за сетевую связность там, где требуется доступ к адресам устройств. Эти роли не подменяют друг друга.

### Эксплуатация

| Инструмент | Роль в системе |
|---|---|
| OpenSSH и Dropbear | Административный вход на серверы и шлюзы по SSH |
| autossh | Поддержание обратных SSH-туннелей как дополнительного пути управления |
| Karing | Клиентское подключение на рабочих устройствах, применение профилей и правил маршрутизации |
| Shell, Python и jq | Сборка списков маршрутизации, операции с API, проверки и обработка конфигураций |
| cron | Плановые проверки и обновление списков |
| curl и штатные сетевые утилиты | Проверки DNS, HTTP, соединений и доступности сервисов |
| Собственный сторож туннелей и Telegram Bot API | Уведомления о потере обратного канала управления и его восстановлении |

Сторож обратного туннеля показывает состояние этого канала, а не качество интернета у пользователей. Проверки приложений с клиентского устройства проводятся отдельно. Перезапуск служб средствами procd или systemd также не заменяет контроль работоспособности приложения.

## Выбор транспорта

Для связности между сетями используется WireGuard или другой сетевой VPN с явным адресным планом и правилами доступа. Для каждого устройства выпускается отдельная пара ключей.

При необходимости прикладного проксирования можно использовать sing-box или Xray с подходящим транспортом, например Hysteria2 или VLESS. Прикладной прокси сам по себе не создаёт полноценную связность между подсетями. Маршруты к корпоративным ресурсам и доступ к устройствам проектируются отдельно.

Выбор транспорта подтверждается проверками TCP, UDP, DNS и рабочих приложений через сети реальных провайдеров. Успешный тест веб-страницы не подтверждает работу телефонии, видеосвязи или других приложений с UDP.

## Адресация и маршрутизация

Для каждой площадки выделяется собственная подсеть. Адреса филиалов, служебного контура и сетей сотрудников не должны пересекаться. При конфликте подсетей его устраняют на этапе проекта, а не маскируют случайными маршрутами.

Правила строятся по назначению трафика:

- корпоративные ресурсы — через разрешённые межсетевые соединения;
- локальные сервисы — внутри площадки;
- интернет-трафик — напрямую либо через выбранный узел по политике компании;
- управление — через отдельный служебный маршрут.

Если локальный выход разрешён, отказ центрального узла не должен блокировать весь интернет филиала. Для ресурсов, которые допускаются только через VPN, применяется явный запрет выхода в обход туннеля. Эти требования фиксируются отдельно для каждой категории трафика.

Общий набор правил хранится в одном источнике. Перед публикацией проверяются синтаксис, пересечения, приоритеты и доступность критичных сервисов. Предыдущая рабочая версия сохраняется для отката.

## DNS без зависимости от пользовательского туннеля

Адреса узлов управления должны разрешаться даже при остановленном сервисе передачи трафика. Иначе получается замкнутая зависимость: чтобы поднять туннель, нужен DNS, работающий только через этот туннель.

Для служебных доменов назначаются прямые резолверы. Их доступность проверяется с каждого филиала. Если требуется независимость от отказа одного оператора DNS, резолверы выбираются у разных операторов.

На OpenWrt нужно различать три настройки:

1. DNS внешнего интерфейса, полученный от провайдера или заданный вручную.
2. Локальный DNS, которым пользуются устройства площадки.
3. DNS внутри сервиса маршрутизации или проксирования.

Изменение первого не гарантирует изменение остальных. Если сервис генерирует конфигурацию локального DNS заново, исключения управления сохраняются в поддерживаемом постоянном файле, а затем проверяются после перезапуска сервиса.

При смене адреса центрального узла клиент должен повторно разрешить его имя. Не каждый VPN-клиент делает это сам: для него предусматривается обновление endpoint или переподключение. Доменное имя без этой проверки не решает проблему устаревшего адреса.

Устройства за дополнительным роутером могут использовать собственный DNS. При доменной маршрутизации это способно привести к обходу правил. Такой случай проверяется отдельно; принудительный перехват DNS вводится только для согласованных устройств и сетей.

## Управление и доступы

Служебная сеть даёт возможность подключиться к оборудованию, но сама по себе не разрешает все действия. Межсетевые правила ограничивают, кто и к каким системам может обращаться.

- Вход администратора — по индивидуальному ключу или учётной записи.
- Доступ к панели управления — из служебной сети, без открытой публикации в интернет.
- Для подрядчика — ограниченный набор ресурсов и срок доступа.
- Увольнение или завершение работ — отзыв соответствующих ключей и разрешений.
- Привилегированные действия — с журналированием и разделением ролей.

Ключ устройства в WireGuard идентифицирует устройство. Если нужна проверка личности сотрудника и многофакторная аутентификация, их реализуют на отдельном шлюзе доступа или в прикладной системе. Панель выдачи профилей не заменяет эту проверку.

Дополнительный обратный SSH-туннель может использоваться как аварийный канал. Его учётная запись ограничивается необходимым перенаправлением портов. Порты управления на принимающем сервере не публикуются для произвольных внешних подключений.

## Отказоустойчивость шлюза

После пропадания питания шлюз должен загружаться без участия администратора. Проверка проводится физическим отключением питания, а не только командой перезагрузки.

На оборудовании без часов реального времени синхронизация времени не должна зависеть от ещё неработающего защищённого соединения. Неверные часы могут нарушить проверку сертификатов и остановить запуск сервисов.

Списки маршрутизации и необходимые конфигурации хранятся в постоянной памяти. Обновление сначала загружается во временный файл, проверяется и только затем заменяет рабочую версию. При недоступном источнике используется последняя исправная копия.

Аппаратный watchdog помогает при зависании устройства. Программное восстановление выстраивается поэтапно: повторная проверка, восстановление конкретной службы, переключение канала и лишь затем перезагрузка. Число перезагрузок ограничивается, чтобы недоступный сервер не превратил исправный шлюз в бесконечно перезапускающееся устройство.

## Ввод филиала

1. Проверить параметры провайдера, существующие подсети и требования рабочих приложений.
2. Назначить площадке идентификатор и адресный диапазон из общего реестра.
3. Настроить локальную сеть и проверить прямой интернет.
4. Выпустить индивидуальные ключи, заранее разрешить их на принимающих узлах.
5. Поднять служебный контур и проверить вход с рабочей станции администратора.
6. Настроить независимый DNS адресов управления.
7. Подключить основной и резервный узлы передачи трафика.
8. Применить маршрутизацию и проверить приложения с клиентского устройства за шлюзом.
9. Выполнить проверки отказов, сохранить резервную копию и записать результат в реестр.

Ключи разрешаются до запуска автоматически переподключающихся клиентов. Иначе защитные механизмы сервера могут заблокировать площадку за повторные неудачные попытки входа.

## Приёмочные проверки

| Сценарий | Ожидаемый результат |
|---|---|
| Основной узел остановлен | Разрешённые сервисы доступны через резерв, управление сохраняется |
| Сервис пользовательского туннеля остановлен | Адрес управления разрешается, администратор подключается |
| Один DNS-резолвер не отвечает | Служебные домены разрешаются через второй |
| Источник списков недоступен | Сохраняется последняя проверенная версия правил |
| Изменилась внешняя адресация узла | Endpoint обновляется по DNS, соединение восстанавливается |
| Пропало и вернулось питание | Шлюз запускается, время и сервисы восстанавливаются |
| Между шлюзом и клиентом стоит ещё один роутер | Проверены его DNS, NAT и доступ к рабочим приложениям |
| Отозван ключ сотрудника или подрядчика | Доступ прекращён без остановки остальных пользователей |

Тест проводится с клиента внутри филиала. Ответ сайта с самого шлюза подтверждает только путь этого шлюза. Наличие процесса, рукопожатия или открытого порта также не подтверждает работу приложения.

## Изменения и сопровождение

Перед изменением сохраняется затрагиваемая конфигурация и проверяется действующий путь управления. Сначала обновляется одна площадка. После проверки результата изменение последовательно применяется к остальным. Для критичных площадок назначается согласованное окно.

Если настройка может оборвать доступ, заранее готовится автоматический откат. Он отменяется только после новой успешной административной сессии и проверки нужных сервисов. Одновременная замена всех каналов управления исключается.

В реестре площадок фиксируются версия конфигурации, дата проверки, доступные каналы, зависимости и незавершённые работы. Фактический результат отделяется от предположений: «туннель поднят» и «рабочая система доступна пользователю» — разные состояния.

Ни один транспорт не гарантирует постоянную связь. Результат этой схемы — меньше общих причин отказа, проверяемое переключение и понятный порядок восстановления.
